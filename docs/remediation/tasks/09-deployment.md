# 09 — Умовний крок: CORS і довірений proxy

Модель: GPT-5.6 Terra / medium. Виконувати лише коли відомі frontend origins, reverse proxy і доступність backend напряму. Спочатку знайди ці дані в конфігах/README; якщо їх немає — коротко запитай, продовжувати залежне налаштування навмання не можна.

Якщо застосунок використовується лише з same-origin Swagger і напряму — SKIPPED з цим обґрунтуванням. Якщо розгортання за proxy або окремий frontend уже потрібні, відсутність даних — BLOCKED, не SKIPPED.

Файли: SecurityConfiguration.java, конфіг properties/application, AuthController.java/AuthRateLimiter.java для перевірки контракту, ops proxy-конфіг за наявності, README і security-тести.

- CORS: явний allowlist з конфігурації; порожній список за замовчуванням. Дозволити лише потрібні methods/headers, включно з Authorization. Credentials лише за потреби фактичної cookie-схеми; не wildcard із credentials. Перевір preflight у справжньому security chain.
- Proxy: використовувати штатну обробку forwarded headers з визначеною межею довіри. Edge видаляє/перезаписує вхідні forwarded headers, backend не довіряє довільному клієнтському X-Forwarded-For. Не парсити перший IP зі строки вручну.
- Тести: два клієнти за довіреним proxy мають окремі лічильники; forged header напряму не обходить rate limit; дозволений origin працює, сторонній не отримує CORS-дозволу. Якщо захист забезпечує мережа, локальний mock-header тест не є повним підтвердженням deployment security — зафіксувати потрібну перевірку edge.
- Багаторепліковий глобальний ліміт: документувати наявне обмеження. Redis не додавати без окремої задачі й реальної вимоги.

Готово: конфіг узгоджений із реальною топологією, тести й операційні вимоги записані. Не змінювати compose на публічне розгортання лише заради цієї картки.
