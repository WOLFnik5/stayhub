# 04 — Email у всіх шляхах запису й входу

Модель: GPT-5.6 Terra / medium. Передумова: 03.

Файли: AuthService.java, UserService.java, service/validation, UserRepositoryImpl.java, email DTO/валідація, нова Liquibase-міграція й master, auth/user/persistence/migration тести.

Обрана політика продукту: email для ідентифікації акаунта нечутливий до регістру; зберігається `trim().toLowerCase(Locale.ROOT)`. Це політика цього застосунку. Не змінювати паролі, імена або довільні текстові поля.

1. Один невеликий helper email-нормалізації. Використати в register, login, PUT /users/me і PATCH /users/me. Для PATCH null зберігає старе значення; blank не допускається.
2. Перевірити межу DTO validation: обіцяні пробіли навколо email повинні оброблятися до @Email або еквівалентної перевірки. Не залишити нормалізацію в сервісі, до якої HTTP-запит не доходить. Не послаблювати перевірку формату адреси.
3. Нова міграція спочатку перевіряє конфлікти після нормалізації, потім нормалізує існуючі значення. При конфлікті — HALT із зрозумілою причиною без видалення/злиття користувачів.
4. БД має гарантувати цю ж політику при конкурентних insert/update: звичайний unique разом із обмеженням канонічного запису або узгоджений unique expression index. Обери один простий спосіб, не додавай citext-розширення без потреби. Перевір відповідність SQL-нормалізації Java для прийнятого набору адрес.
5. Перехоплення унікального конфлікту має давати узгоджену зрозумілу відповідь і для гонки; не перетворюй будь-який DataIntegrityViolation на «email зайнятий».
6. Документуй: нормалізація даних незворотно змінює початкове написання email. Rollback DDL не відновлює регістр; не обіцяй повного відкату даних.

Критерії: змішаний регістр/пробіли працюють у register/login/PUT/PATCH згідно з політикою; дубль відхиляється; два конкурентні запити не створюють два акаунти; plain SQL не обходить інваріант; міграція працює на порожній і старій чистій БД та зупиняється на конфліктній без втрати даних. Перевір сценарій зміни тільки регістру власного email.

Тести: AuthServiceTest, UserServiceTest, AuthControllerIntegrationTest, UserControllerIntegrationTest, LiquibaseMigrationIntegrationTest і нові перевірки унікальності. Не виконувати нормалізацію реальної БД вручну.
