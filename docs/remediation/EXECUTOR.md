# Спільні інструкції виконавцю

Виконуй тільки вказану картку. План фіксує обсяг роботи; не починай сусідні задачі й не перепроєктовуй застосунок. Читай застосовні AGENTS.md, якщо вони з'являться. Працюй автономно в межах картки; питання потрібне лише для відсутнього бізнесового рішення, недоступного середовища або дії поза дозволами.

## Перед змінами

1. Прочитай свою картку та STATUS.md. Перевір передумови.
2. Виконай `git status --short`, переглянь diff тільки файлів своєї задачі. Збережи чужі незакомічені зміни. Не роби reset, checkout файлів, stash, масове форматування або автоматичний commit/push.
3. Перевір, чи проблему вже виправлено. Якщо критерії вже виконані, покажи докази й познач PASS без зайвих правок.
4. Знайди релевантні тести через `rg --files src/test/java`, не вигадуй назви наявних тестів. У картках названо відомі класи; нові тести додавати поруч.

На момент підготовки змінені BookingRepositoryImpl.java, ReadableLoggingTest.java, PersistenceIntegrationTest.java, BookingCheckoutIntegrationTest.java; є й untracked файли. Актуальний `git status` важливіший за цей список. Новий worktree без перенесення цих змін не відтворює перевірену версію.

## Реалізація

- Зроби найменшу завершену зміну, включно з безпосередніми викликачами й потрібними тестами. Якщо потрібний файл поза початковим переліком, коротко обґрунтуй його зв'язок; не розширюй бізнесовий обсяг.
- Зберігай блокування бронювань, транзакційний outbox, claimToken, ключі ідемпотентності Stripe, перевірки суми/валюти/metadata і перевірку підпису вебхука.
- Не змінюй уже застосовані Liquibase changeset. Схему змінюй новою міграцією з наступним вільним номером та реєстрацією в master.
- Не викликай справжні Stripe/Telegram операції для перевірки. Використовуй наявні моки й Testcontainers. Не виводь .env, токени, паролі чи HTTP Authorization у звіт.
- Не переписуй assertion під отриманий результат без перевірки контракту. Не вимикай тести, coverage або Checkstyle і не збільшуй sleep для маскування гонки.

## Перевірка

Код проєкту орієнтований на Java 21. Перевір `java -version` і `mvn -version`; використовуй сумісне налаштоване середовище. Не змінюй pom або системний JDK лише заради локального запуску. Testcontainers потребує доступного Docker. Якщо середовище недоступне, явно познач неперевірені критерії; це не дефект застосунку і не успішна перевірка.

Команда вибіркової перевірки в PowerShell:

```powershell
mvn '-Dtest=AuthServiceTest,AuthControllerIntegrationTest' test
```

Список заміни класами своєї картки; додай нові класи. Не передавай shell аргумент `-Dtest` з комами без лапок. `mvn ... test` проходить compile, де підключено Checkstyle. Після поведінкових правок запускай мінімальну релевантну групу. Для простого видалення зайвої залежності або недосяжного методу достатні компіляція/наявні тести, нові тести заради кількості не потрібні.

Логи великих прогонів можна зберігати в ігнорованому `target/remediation/` після clean або в тимчасовому каталозі. У відповідь виводь підсумок і діагностичний фрагмент. Не запускай той самий невдалий прогін повторно без зміни гіпотези, коду чи середовища. Якщо команда вперлася в дозволи, використовуй встановлений механізм запиту дозволу, не обхід.

## Передача й результат

Після максимум двох невдалих спроб усунути одну причину зупини цей цикл і підготуй передачу сильнішій моделі. Зміна бізнесового контракту, міграція з конфліктними даними або проблема конкурентності поза карткою також потребують окремої передачі, а не випадкового виправлення.

Онови лише рядок своєї задачі в STATUS.md і додай короткий запис:

```text
ID / модель / дата:
Статус: PASS | FAIL | BLOCKED | NEEDS_REVIEW | SKIPPED (лише умовний крок 09)
Зміна: 1–3 речення.
Файли: короткий перелік.
Перевірка: точна команда, exit code, tests/failures/errors/skipped.
Невиконані критерії / обмеження:
Наступний виконавець: лише необхідні рішення або проблеми.
```

Не позначай PASS за старими surefire-звітами. Відрізняй повторювану початкову помилку від регресії свого патча. Завершальна відповідь — до 10 рядків плюс потрібний діагностичний фрагмент.
