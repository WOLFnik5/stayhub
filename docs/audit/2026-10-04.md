# Аудит StayHub — 4 жовтня 2026

## Висновок і рівень

Це сильний backend pet/MVP, який за інженерними рішеннями відповідає рівню Middle. Транзакційний outbox, захист місткості в PostgreSQL, перевірка Stripe webhook, конкурентні інтеграційні тести, tracing і контрольоване розгортання виходять за межі базового CRUD. Водночас життєвий цикл бронювання й платежів має прогалини, які заважають безпечній роботі з реальними клієнтами. Поточний стан не дає підстав називати систему готовою до production.

Це оцінка артефакту, а не підтвердження професійного рівня автора. Кількість технологій сама по собі не є показником якості.

| Напрям | Оцінка | Підстава |
| --- | --- | --- |
| Архітектура | Добра база, потребує спрощення залежностей | Виділені HTTP, сервіси, persistence, адаптери; бізнес-сервіси залежать від конкретних repositories і HTTP DTO |
| Конкурентність і цілісність | Сильна сторона | Pessimistic locks, PostgreSQL triggers, FK, unique pending payment, outbox claim token |
| Бізнес-модель | Потребує завершення | Немає строку утримання неоплаченого бронювання; оплата не підтверджує booking; немає refund/reconciliation workflow |
| Безпека | Базові механізми є, deployment hardening неповний | BCrypt, JWT, ownership checks; superuser для runtime БД, відкриті dev-порти, локальний rate limit |
| Тести | Змістовна база, повний результат цього аудиту не підтверджено | Є race tests і реальний PostgreSQL; Docker недоступний під час перевірки |
| Експлуатація | Добра локальна підготовка | Метрики, alerts, immutable image deployment; немає зовнішнього alert receiver і перевіреного backup/restore |

## Інші недоліки й практичні обмеження

- **At-least-once notifications.** Consumer робить `isProcessed → Telegram send → markProcessed`. Crash після прийняття повідомлення Telegram до DB mark або concurrent delivery того самого event може дати повторне повідомлення. Unique inbox row цього не усуває, бо insert відбувається після зовнішнього ефекту. Це вже коректно згадано в README; не варто обіцяти exactly-once. Додати delivery states, контроль concurrent claims і tolerance до повторів. Саме по собі переставлення `markProcessed` перед send створить ризик втрати повідомлення.
- **Recovery подій.** Є DEAD/DLT і alerts, але немає реалізованого керованого replay workflow. `processed_events` не має cleanup у main-коді; retention слід узгоджувати з максимальною replay window. Outbox відправляє batch послідовно через `.join()`, тому timeout broker може значно затримати доставку. Реальний drain throughput не виміряний у наявних API stress tests.
- **Accounts.** Немає email verification, password reset/change, account lock/deactivation або logout/revocation для конкретного token/session. JWT може лишатися чинним до 60 хвилин; DB user lookup правильно застосовує зміну ролі на наступному запиті, але не є session revocation. Refresh tokens не обов'язкові для MVP; якщо їх додавати, потрібні rotation і reuse detection.
- **Sensitive logging.** Профіль `dev` вмикає SQL bind `TRACE`, що може записувати email, profile fields і password hashes. Default profile уже без цього tracing. Реальні дані не повинні потрапляти в dev diagnostics. Потрібні production profile policy, redaction і retention.
- **Alerts без доставки.** `ops/monitoring/alertmanager.yml` має порожній `local-only` receiver. Alerts видимі локально, але ніхто не отримує зовнішнього сповіщення. Це не слід плутати з бізнесовими Telegram notifications. Налаштувати receiver і провести test alert.
- **Backup і доступність.** Немає автоматизованого backup/restore/PITR workflow, визначених RPO/RTO й перевіреної процедури відновлення. Compose має одну БД і один Kafka broker, replication factor 1. Deployment replacement має downtime; rollback відновлює image, але не DB schema. Це частково вже чесно описано в deployment README.
- **Обсяг обробки.** Expiration завантажує всі eligible bookings списком. Booking capacity query виконує correlated counts для candidate dates; його вартість залежить від активного календаря. Додати batch expiration, EXPLAIN ANALYZE на реалістичних active bookings і тест hotspot accommodation. У всіх paging repositories є `page * size` у `int`, без захисту від overflow; величезний page може завершитися помилкою або неправильною сторінкою.
- **Архітектура.** `service` імпортує HTTP DTO і concrete `*RepositoryImpl`; назва `Impl` не підкріплена відповідними business repository interfaces. README описує інше розміщення шарів. Сервіси варто перевести на application commands/results і невеликі ports, а state transitions — з довільних setters у явні операції. Переписування всього в microservices не потрібне.
- **Керовані налаштування.** Час checkout і expiration залежить від `LocalDate.now()`/`ZoneId.systemDefault()`. За різних timezone на Windows/Linux поведінка може змінюватися біля опівночі. Додати явний business timezone і `Clock`. DTO не обмежують довжини names/location/amenities відповідно до DB schema; потрібні узгоджені межі і `@Digits` для money fields.
- **Документація і reproducibility.** Є застарілий remediation status із попередньою невдалою збіркою та новіші verification docs із успішною; потрібне одне актуальне джерело стану. Наявні локальні load reports не доводять production capacity: Stripe, Telegram і Kafka delivery виключені, generator і API працювали на одному host. CI actions і Docker base images не pinned до digest/SHA; додати контрольоване оновлення й supply-chain metadata.

## Що реалізовано добре

- Ownership checks для bookings/payments і admin-only catalog/role changes; customer list queries примусово використовують власний user ID.
- Реєстрація не приймає role від клієнта; пароль хешується, JWT secret перевіряється за decoded key length.
- JWT signature/expiration перевіряються, current user/role береться з БД; зміна email не ламає ідентифікацію через immutable user ID.
- SQL/JPQL використовують bound parameters; очевидного user-input SQL concatenation у перевірених запитах не знайдено.
- Webhook перевіряє Stripe signature; success/cancel landing endpoints не підтверджують payment і не видають деталі чужого платежу.
- Checkout має durable attempt і стабільний idempotency key; перевіряються remote amount/currency/booking metadata.
- Capacity захищена на рівні сервісу й PostgreSQL; обчислення враховує максимальну одночасну зайнятість, а не суму всіх перетинів.
- Transactional outbox, `SKIP LOCKED`, lease/claim token, retry і DLT дають основу для надійного async delivery.
- Catalog pagination уникає collection fetch pagination/N+1 через окремий вибір IDs і bulk amenities fetch; Open Session in View вимкнено.
- Prometheus endpoint має окремого обмеженого reader; є correlation ID, tracing, queue metrics, test rules.
- CI запускає verify, deployment використовує immutable application digest, health checks, `flock` і rollback; контейнер застосунку працює без root.

Вимкнений CSRF для stateless bearer API сам по собі не визначено як вразливість. Відсутність відкритого CORS allowlist також не є доказом permissive CORS. Swagger у public access — свідомий вибір API visibility, а не автоматично критичний дефект.

## Що додати: рекомендований порядок

1. **Завершити бронювання й оплату:** hold deadline, підтвердження booking, reconciliation, refund/cancellation policy, agreed price snapshot. Це головна цінність наступної ітерації.
2. **Закрити вхідні помилки й небезпечні defaults:** password validation, JSON/type errors, DB roles, loopback dev ports, timezone, Kafka security properties; актуалізувати залежності.
3. **Додати перевірки бізнес-інваріантів:** paid → confirmed, old unresolved attempt recovery, hold vs webhook race, concurrent demotion/profile update, real Kafka outage/recovery. Перезапустити повний verify з Docker; встановити branch coverage gate для критичних payment/booking flows.
4. **Підготувати експлуатацію:** backup + restore drill, alert receiver, replay/reconciliation admin tools, account revocation, audit trail admin/payment changes, deadlines і latency objectives.
5. **Покращити продукт:** пошук за датами/місцем/ціною/типом/amenities, реальна доступність на діапазон дат, фотографії, guest capacity, підтвердження email і відновлення доступу, історія оплати/refund. Reviews і favorites доречні після завершення основного lifecycle.
6. **Масштабувати за вимірами:** окремо виміряти authenticated reads, hotspot booking writes, outbox drain, provider timeouts і тривале навантаження. Shared limiter або read cache додавати за потребою; Kafka/Redis/microservices не є самостійною метою.

Найважливіший наступний крок — зробити життєвий цикл booking/payment цілісним і відновлюваним. Сильна інфраструктура вже є; найбільший виграш зараз дасть завершення бізнесових інваріантів і operational recovery.
